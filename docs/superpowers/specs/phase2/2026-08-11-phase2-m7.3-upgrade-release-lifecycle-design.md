# P2-M7.3 — Upgrade & release lifecycle (design)

**Status:** draft.
**Track:** the P2-M7.x field-findings remediation track (`docs/ROADMAP.md`).
**Closes:** field-findings §23.
**Depends on:** P2-M7.2 (commit `143c459`).
**Blocks:** P2-M7.4.

## Why this milestone exists

`docs/VERSIONING.md` defines four version axes and a unique stamp per build; the
cross-version gate tests both mixed directions. None of it reaches the
deployment. The shipped coordinator is built from a `git clone` with no version
stamp and reports itself as `dev`. The donor binary has no version symbol. Schema
migrations apply as a side effect of container start. Nothing records what was
upgraded, when, or from what.

§23's three questions — **what order do I upgrade, how do I prove it worked, and
exactly how do I go back** — are unanswerable, not because the answers are hard
but because the system has no way to state them.

Three layers, in order: **produce identity** (releases that can be named),
**report identity** (a running system that says what it is, with honest trust
labels), **contract on identity** (compatibility, obligations and procedures,
generated from one source and bound to executed evidence).

## Decisions

### D-M7.3-1 — The baseline is a commit; three tag namespaces.

**The precontract baseline is commit `143c459`, schema 18, locally built
images** — what every existing deployment runs. "P2-M7.2" is a human label in
prose. The remote tag namespace holds only the two lightweight
`v0.2.0-beta.1+…` refs (row 18), so no milestone tag can be cited as published;
a commit SHA is correct regardless and verifiable offline.

- **Product releases** — `vMAJOR.MINOR.PATCH[-prerelease]`, strict SemVer, no
  build metadata (`+` is not a legal Docker tag character, and SemVer ignores it
  for precedence).
- **Milestone tags** — local history.
- **Historical release-shaped tags** — the `v0.2.0-beta.1+…` refs, and local
  `v0.1.0-rc1`. They predate this contract; the `+ad629d7` commit message calls
  `0.2.0-beta.1` "the release", so they are described as *pre-contract release
  identifiers*, not as never having been releases. No compatibility claim
  references them.

**M7.3 is `v0.3.0`.** Pre-1.0 SemVer permits a minor bump for breaking changes;
this one changes the deployment shape, adds schema 19 and adds wire fields.

Tag-namespace reconciliation is out of scope and recorded as an open item.

### D-M7.3-2 — Release intent, release lock, and the trust between them.

#### D-M7.3-2a — The trust root is out-of-band, and it is not the bundle.

Trust must not originate in the material being verified. Two rejected shapes:

- **Rejected:** the target artifact authenticates the document that authorizes
  the target artifact. A malicious bundle names a malicious admin image that
  blesses the same bundle.
- **Rejected:** the bundle carries both the verification script and the signer
  policy. A substituted script skips verification; a substituted policy
  authorizes the attacker's signer. Cosign requires the *verifier* to supply the
  expected certificate identity and issuer — the executable alone is not a
  policy.

The trust root is therefore **the host's Cosign installation plus an
out-of-band Nova signer policy**, and the order is:

1. The operator runs a **minimal, fixed `cosign verify-blob`** with the issuer
   and workflow identity **hard-coded in the documented command**, not read from
   the bundle, against the release lock. Nothing from the bundle has executed.
2. The authenticated lock names `scripts/nova-release`'s exact hash. Only now may
   it run.
3. The orchestrator verifies `nova-admin@<digest>` — the digest coming from the
   authenticated lock — for signature and provenance.
4. It pulls and invokes that exact digest. The target admin cross-checks its
   embedded catalog against the authenticated lock as a **consistency check**,
   never as the authentication.

Subsequent releases may use a bootstrap installed by the previous trusted
release. The bundle's copy of the verification policy is an **auditable
artifact**, not the authority.

**Every bundle member's hash is covered by the signed lock** (or by a separately
signed manifest). An attacker must not be able to modify a file and its own hash
entry together.

#### D-M7.3-2b — Intent declares claims; only the lock asserts proof.

Intent is reviewed before any build exists, so it cannot carry evidence.

- **Intent** declares *requested* claims, the capabilities each requires, and
  **which gate must prove it**. Its claim type carries no evidence field.
- **The lock** binds each claim to successful evidence from the exact candidate
  digests. Proven claims are a lock-only type.

**Rejected:** run IDs as archival evidence — logs expire. Evidence is a **signed
statement** carrying artifact digests, source commit, scenario and capability
IDs, test revision, outcome, timestamps and runner class; the lock records the
statements' content digests and they are attached to the release.

#### D-M7.3-2c — The embedded catalog.

`internal/release/catalog_gen.go` is generated from the checked-in intent and
compiled into every binary: version, exact intent digest, source-revision policy,
target schema, platform, the supported-window metadata (D-M7.3-21), and artifact
repositories. It makes `upgrade status` work offline and is what the target admin
compares against. No filesystem or network dependency (T1.22).

#### D-M7.3-2d — The release bundle.

Exactly: the intent bytes; the signed lock; the Sigstore bundle and certificate;
an auditable copy of the verification policy; the signed evidence statements; the
release Compose environment; a release-specific `UPGRADING.md`; `nova-release`;
and a hash manifest covering every member, itself covered by the lock.

**The Compose environment must be covered by the signed lock**, or generated only
after verification. Signing the description while the deployment reads something
else is the whole attack.

**The authentication graph is acyclic.** A lock cannot hash itself, cannot hash
a manifest that hashes the lock, and cannot hash its own Sigstore bundle — that
bundle *contains the signature over the lock*. The exact shape:

```
lock.sigstore.json  ──authenticates──▶  lock (exact bytes)
lock                ──hashes──────────▶  every payload member
                                          (intent, policy copy, evidence,
                                           compose env, UPGRADING.md,
                                           scripts/nova-release)
lock                ──hashes──────────▶  hashes.txt   (optional, derived)
hashes.txt          ──derived from────▶  the lock's payload map
                        (covers no lock, no signature envelope, not itself)
```

Root: `lock.sigstore.json`. Excluded from hashing: the lock itself and its
authentication envelope. `hashes.txt` is a human-readable convenience derived
from the payload map, never an authority. Tests prove the graph is acyclic and
that **every deployable payload byte has exactly one authenticated path** —
neither zero nor two.

#### D-M7.3-2e — Build once, promote, then tag.

```
intent merged at source S
  → build + push candidate descriptors ONCE
  → SBOM, provenance, sign, attest the candidate digests
  → verify those materials
  → run gates; emit signed evidence statements
  → finalize + sign the lock
  → approval
  → promote OCI refs, READ BACK, assert digest AND mediaType match the lock
  → create the Git product tag  ← only after successful read-back
  → publish the immutable release
```

The Git tag is created **after** promotion succeeds, so a failed promotion or
read-back leaves no product-shaped tag. Git tags and OCI tags are distinguished
throughout, and the sequence supports **idempotent recovery between any two
external writes**. Tag creation belongs exclusively to this state machine; no
other procedure creates a product tag.

The trigger is a candidate ref. Binaries are stamped with the intended **final**
version at candidate build, because those exact bytes are promoted.

**Promotion is not digest-neutral by default.** `docker buildx imagetools create`
creates a new index when given a single-platform manifest; an existing index is
carbon-copied. The workflow either standardizes candidates as OCI indexes or
passes `--prefer-index=false`, and asserts the read-back match either way.

`VERSIONING.md` states plainly that **a rebuild after the lock commit will not
reproduce the digest**, and that this is expected. **Rejected:** claiming
reproducibility that the build does not provide.

### D-M7.3-3 — Three released artifacts, consumed by both production topologies.

`nova-coordinator`, `nova-node`, `nova-admin` — each stamped, labelled, signed,
SBOM'd, provenance-attested and locked. Across the two canonical production
topologies: the **operator** topology consumes coordinator and admin (the latter
for both `nova-admin` and `nova-doctor`, preserving their different mounts); the
**donor** topology consumes node. `deploy/operator/compose.federation.yaml` moves
off local `build:` (row 27) — publishing a third artifact while production builds
it locally finishes nothing.

The release environment is separate from `docker/.env`, which carries operator
secrets, with ordered `--env-file` use and atomic activation so preflight can run
the target admin without disturbing the running coordinator.

### D-M7.3-4 — Build-context hygiene (P0-a).

Once digests are contractual, an uncontrolled context is a leak path and a
nondeterminism source that would be misattributed to the release process.

### D-M7.3-5 — Runtime metadata: embedded catalog for status, verified bundle for planning.

T1.22 forbids fetching. Three things: **embedded build info** (what this binary
is), **the embedded catalog** (what this build claims), and **the target release
bundle** (operator-supplied, verified per D-M7.3-2a, mounted read-only).
`upgrade check` runs from the target `nova-admin`, because an N−1 deployment
cannot otherwise evaluate an N target.

### D-M7.3-6 — Reported, expected, observed.

#### D-M7.3-6a — Two kinds of donor claim, with different powers.

A process cannot discover its own OCI manifest digest without runtime
cooperation, and Nova gives neither coordinator nor doctor a Docker socket. So
`NOVA_NODE_IMAGE_DIGEST` and `NOVA_NODE_BUNDLE_LOCK_DIGEST` are **configured
declarations** and a donor may report anything.

Donor claims split into two classes with different authority, and conflating
them is what makes "reported never gates anything" and "a capability change
alters role eligibility" read as a contradiction:

- **Identity claims** — `reported_client_version`, `reported_image_digest`,
  `reported_bundle_lock_digest`. **Census-only.** They never gate protocol
  access, placement, durability counting, trust graduation, drain or eviction. A
  mismatch against the operator's `expected_*` value is a supply-chain warning.
- **Capability advertisements** — what the donor says it can *do*. These **do**
  gate routing, and always have: a donor that does not implement
  `read-source/v1` must not be sent read-source work. That is a routing decision,
  not a security authorization — a lying donor can only deny itself work or
  accept work it will fail, both of which the existing failure paths handle,
  and neither of which grants it access to anything.

**One operational source.** All capability predicates read
`effective_capabilities`, and only that: `federation.sql` (admission,
read-source), `replication.sql` (read, repair, healing placement),
`storage_state.sql` (sourceability, pruning safety), and `possession.sql` (audit
eligibility) are migrated together. A second source is how a role predicate
silently keeps consulting a stale set.

Reported values are length- and syntax-validated despite being untrusted.

#### D-M7.3-6b — The operator's expectation is stored, and rollout is a command.

Migration 0019 adds per-node `expected_image_digest`,
`expected_bundle_lock_digest`, `expected_at` and `expected_by` — and, on the
reported side, **`reported_bundle_lock_digest`** with its
`RuntimeContract.BundleLockDigest` field and the donor Compose environment that
supplies it. Storing an expectation with no counterpart to compare it against
would leave the operator unable to confirm the bundle-level rollout they
authorized; image digest and bundle-lock digest are separate census relations
because a donor can match one and not the other.

Storage without a command is inert, so the operator surface is explicit:

```
novactl node rollout authorize --node-id <id> --lock <verified-lock>
```

It requires an already-verified lock, persists both expected digests, records
actor and time, writes the privileged audit event (T1.24), and may initiate or
require the existing drain. It never runs from the volunteer script.

The two-party path: operator authorizes → operator drains → volunteer applies →
donor reports its configured declaration → operator confirms match and health →
operator undrains.

### D-M7.3-7 — The runtime contract on the heartbeat.

#### D-M7.3-7a — One versioned object, not independently optional fields.

Version and digest presence-clear directly. Capabilities and protocols cannot,
because **a legacy donor that never sent them and a rolled-back donor that
stopped sending them produce the identical wire message**. No handler logic
distinguishes them.

The heartbeat therefore carries **one nested, versioned `runtime_contract`
object** rather than independently optional fields, so a partial update cannot
compose an impossible state, and migration 0019 persists
`runtime_contract_observed_at`:

- **Never observed** ⇒ omission means *legacy*. Retain the registration snapshot;
  classify runtime-contract freshness as `registration-only`.
- **Observed at least once** ⇒ omission means *downgrade*. Mark the runtime
  contract unknown and **remove stale optional-role eligibility**.

Donor-advertised protocols are stored **separately from `selected_protocol`**,
which is the coordinator's negotiated session outcome (`handlers.go:115,130`) and
never a donor claim. A protocol change requires re-registration or an explicit
renegotiation handshake.

`handlers.go:165-185` ignores every decode error, not only `io.EOF`. An empty
legacy body is accepted; malformed or trailing JSON is rejected.

#### D-M7.3-7b — Why this is a correctness fix.

`replication.sql:147` selects repair sources on
`advertised_capabilities @> ARRAY['repair-stream/v1']`, and `:18` selects read
sources on `read-source/v1`. Both read state written only at registration. A
donor that rolls back today keeps eligibility for a role it no longer implements,
so the coordinator schedules work that will fail.

#### D-M7.3-7c — The capability state machine.

`effective_capabilities` moves through exactly these transitions. Anything not
listed is a defect.

| From | Event | To |
|---|---|---|
| — | registration | registration snapshot; `runtime_contract_observed_at` **NULL** |
| snapshot, marker NULL | heartbeat **with** a supported contract | contract's set; marker **stamped** |
| snapshot, marker NULL | heartbeat **without** a contract | unchanged (legacy donor) |
| runtime, marker set | heartbeat **with** a supported contract | contract's set; marker refreshed |
| runtime, marker set | heartbeat **without** a contract | contract unknown; **optional-role capabilities dropped**, replicas retained |
| any | **re-registration** | fresh snapshot; marker **reset to NULL** |
| any | heartbeat with an **unknown future** `runtime_contract.version` | keep the current set for existing work; **grant no new optional-role work**; record `contract_version_unsupported` |

The re-registration reset is load-bearing: without it, a legacy donor that
re-registers after eviction inherits a stamped marker and its next
contract-less heartbeat is misread as a rollback. The unknown-future-version rule
keeps a newer donor's heartbeat compatible while refusing to infer capabilities
from a schema this coordinator cannot parse — conservative in the direction that
loses work rather than the direction that loses data.

### D-M7.3-8 — Migration obligations are composable and predecessor-relative.

Independent dimensions — `OldBinaryCompatible`, `OnlineApplicable`,
`RequiresMaintenance`, `RestoreToRevert`, `Procedures`, `BootstrapOnly` —
composed across `(applied, target]` as a conjunction of flags and a union of
procedures.

**Rejected:** a single ordinal class with strictest-wins. It cannot express that
`0003_partitions.sql` drops two tables (so reverting needs a restore) while the
recreated tables may still serve an older binary — independent facts on one axis.

**`OldBinaryCompatible` is not intrinsic to a migration.** It is compatibility
with a *named* predecessor; a schema can suit N−1 and not N−2. The flag is bound
to that predecessor, and version-pair assertions live in release scenarios.

`0003.OldBinaryCompatible` is set **conservatively false** pending a historical
binary test: composite primary keys and historical queries may differ even where
recreated tables look similar. **Rejected:** deriving it by inspection.

Classification lives outside the frozen SQL — annotating 0001–0018 would force a
`MANIFEST.sha256` regeneration, setting the precedent that `migrations-frozen` is
negotiable — and is exposed through read-only lookups.

### D-M7.3-9 — Migration application.

#### D-M7.3-9a — One advisory-locked, target-bounded apply.

`migrate apply --to <n> --expect-release-lock <digest> --acknowledge <obligation>`
— advisory lock, re-read the applied schema **under the lock**, compute
`(applied, target]`, refuse anything unexpected, record phases, stop at target.
**Rejected:** `plan` followed by an unbounded `up`, which can apply a different
set than the one reviewed.

The entrypoint auto-applies only when the **whole** range satisfies
`OldBinaryCompatible && OnlineApplicable && !RequiresMaintenance &&
!RestoreToRevert` **and** requires no procedures or acknowledgements; otherwise
it stops with the explicit command. `NOVA_MIGRATE_ON_START=false` hands over
control, and the coordinator then refuses to start against a stale schema.
Boolean parsing accepts only valid values; a typo must not read as `false`.

**`migrate down` is removed from the shipped command surface.** The normative
contract is restore-only rollback (`migrations.go:1-14`); shipping a `down`
subcommand contradicts it and invites exactly the operation the contract
forbids. Down migrations remain in the files for test fixtures; the production
binary does not expose them.

#### D-M7.3-9b — The bootstrap journal.

Migration 0019 creates `upgrade_runs`, so the first upgrade from schema 18 cannot
insert its `started` row before applying it. Sequence: write and fsync a local
journal with the run ID and the preflight/apply-started event → apply 0019 →
backfill the run and pre-0019 events under the **same run ID** → continue
recording to both. If 0019 fails, the journal is the authoritative record.

The report location is designed, not assumed: `nova-admin` and the migrate
service are `run --rm`, so a report on their root filesystem evaporates. An
operator-owned bind mount or named volume, atomic writes, restrictive
permissions, redaction rules, documented backup path.

A **clean schema-0 install** must still apply 0001–0019; `BootstrapOnly` on 0001
must not block a fresh deployment. Upgrade history is **append-preserving** — a
deleted run may not erase its own events — and privileged migration actions are
recorded in `audit_log` (T1.24).

### D-M7.3-10 — Upgrade runs and events.

Run ID; phase (`preflight`/`apply`/`verify`/`rollback`); from/to release and
schema; lock digest; expected artifact digests; acknowledged obligations; config
fingerprint before and after; timestamps; state
(`started`/`passed`/`failed`/`aborted`/`skipped`/`interrupted`); actor;
structured detail. The config fingerprint covers the **effective** configuration,
excludes secrets, and preserves unknown keys.

### D-M7.3-11 — Verification is cross-plane, orchestrated from the host.

One process inside `nova-admin` cannot observe host image digests (no Docker
socket), enter `nova-doctor`'s network namespace, persist a report past its own
removal, or perform host disk checks. Nova's three-plane doctor exists because
these planes do not collapse.

The host orchestrator runs `novactl upgrade verify --plane admin`, `nova-doctor
--plane doctor` in its own service, and host Docker inspection itself, carrying
one run ID and report directory through every invocation and aggregating hashed
per-plane results.

**Requirement and outcome are separate axes**: requirement is
`required`/`optional`; outcome is `passed`/`failed`/`skipped`. A **required
skipped** check blocks by default unless explicitly acknowledged. **Rejected:** a
single enum in which "disk headroom could not be checked" silently permits a
dangerous migration.

The canary is not a soft-deleted blob (row 26). Preference order: an
authenticated donor read-source probe that mutates nothing; a pre-existing
eligible object; a reserved canary with a documented lifecycle.

### D-M7.3-12 — Compatibility evidence.

Three distinct kinds: **wire** compatibility on a fresh DB; **schema upgrade plus
old binary on the forward schema** (nothing tests this today, and it is the only
evidence that can support a rollback-safe claim); and **released-artifact
continuity** using exact candidate digests. `live_upgrade_e2e.sh` keeps proving
M7.2 adoption and is not overloaded.

Scenarios are an **exact coordinator/donor artifact pairing**, not "previous
donor" — N−2 and six-month-supported artifacts cannot be represented otherwise,
and the baseline side must accept a **commit identity** because it has no product
version.

The gate-coverage table records what each gate proves and does not prove, and
scenario validation refuses claims beyond it. The current cross-version gate is
pinned to a stale predecessor whose documented defects (fabricated audit passes,
broken donor-backed reads) are properties of **that binary**, not of previous
coordinators generally; repinning to the baseline and rerunning is what produces
honest coverage. **Rejected:** encoding one binary's defect as a universal
limitation.

### D-M7.3-13 — Census axes.

Baseline donors report nothing, so they are `unknown` — and `unknown` is not
incompatible. Orthogonal properties, never one enum:

- **version compatibility**: current / supported / unsupported / unknown / invalid;
- **freshness**: fresh / stale;
- **digest relation**: match / mismatch / unavailable;
- **runtime-contract freshness**: runtime / registration-only / unknown;
- **negotiated protocol compatibility**;
- **mandatory-profile compliance**;
- **per-role eligibility**.

`ListNodes` gains `client_version` and both the reported and expected columns
(row 12). Classification happens in Go against the compatibility graph; SQL
lexical grouping cannot compare SemVer. `upgrade check` blocks on genuine
protocol or profile incompatibility, or on unresolved drain debt — never on an
untrusted version string.

**The census read path is schema-version-aware.** `upgrade check` runs from the
target `nova-admin` **before** migration, against schema 18, where none of the
0019 columns exist — a generated query naming them fails before preflight can
evaluate anything. So the read path probes the schema version first: at 18 it
queries baseline columns only and synthesizes the unavailable axes as
`unavailable`; from 19 it uses the full census query. This is a prerequisite for
the first-transition scenarios, not a graceful-degradation nicety.

The endpoint is **operator-only** — a nested `RequireRole("operator")` inside the
operator+moderator `/admin` group, following the key-rotation precedent — sets
`Cache-Control: no-store`, and is documented in `openapi.yaml`.

### D-M7.3-14 — The Compose transition.

The digest comes from the release bundle, not a self-referential constant in the
source tree. When `image` and `build` coexist, behaviour depends on
`pull_policy`, so the dev overlay sets `pull_policy: build` explicitly. Multiple
files merge rather than replace, so every documented combination and ordering is
tested — including the live deployment's observed base + override shape, which is
an observed configuration rather than automatic default-file discovery (Nova's
commands pass `-f` explicitly, which suppresses it).

### D-M7.3-15 — Donor bundle schema version 2.

`InviteManifest.Version` bumps to `2`; the field already exists. The lock covers
node, Nebula and Kubo. The updater persists the new lock **atomically before
recreating** — otherwise Compose restarts the old configured digest and the
update silently no-ops — never removes volumes, and binds targets to a
**verified release lock** rather than to anything signed by the repository.

**Rollback is conditional, not automatic.** The donor topology holds Nova node
state, a persistent Kubo repository and Nebula configuration; reverting image
references is unsafe if a newer component has already changed persistent state
incompatibly. The donor lock therefore declares **predecessor-relative rollback
evidence per component**. Automatic lock rollback happens only where that
evidence says it is safe. Otherwise the updater **stops**, preserves the volumes
and both lock files, and emits a recovery report — it does not start older
software against possibly upgraded state. For v0.3.0 this should be cheap to
establish, since the Nebula and Kubo digests are unchanged from the baseline and
only `nova-node` moves.

Existing v1 bundles convert. **Rejected:** reissuing an invite, because `Invite`
mints a new UUID and certificates, which is exactly the re-enrollment the track
forbids. Conversion consumes the existing manifest, Compose, identity and state
and emits only the new lock and update files.

Parties are split: drain and assignment verification are operator-side; the
volunteer script holds no coordinator admin authority.

The cosign identity policy (row 20) changes with the workflow, in one commit
across the donor quickstart, the generated operator README and any bundle-embedded
copy.

### D-M7.3-16 — Release CI.

Extends the existing signing jobs (`ci.yml:231-256,297-319`). Canonical tag
validation; the D-M7.3-2e state machine; three artifacts; explicit platform
policy; every tool pinned by digest; least privilege plus the release permission;
environment approval, concurrency, idempotency, no-overwrite; signature,
provenance and SBOM verification before publication; the updated OIDC policy;
draft → attach lock and evidence → publish immutable.

Signed **OCI descriptors** (digest, mediaType, size, platform, child descriptors)
go in the lock and are validated against the registry at release time; a digest
string alone cannot distinguish an index from a manifest.

**One stable signing principal.** Signing happens in `release.yml` executed from
protected `main`, with the candidate commit passed as an immutable input — not
from a tag ref, which does not exist when the candidate is signed. GitHub's
`workflow_ref` carries both workflow path **and** Git ref, so the identity the
Cosign policy admits is written out exactly rather than left implicit, and it is
the same identity for the first release and every later one.

**The first release's policy is distributed out of band** — it cannot originate
in the bundle it authenticates (D-M7.3-2a). Later releases may ship the next
policy inside the previous authenticated release.

**A verified lock is passed as an authenticated digest, not a path.**
`--lock <file>` means nothing across a process boundary: the receiving process
re-hashes the exact bytes and compares against a digest it was given through the
authenticated chain. Every consumer — `upgrade check`, `upgrade verify`,
`rollout authorize`, the donor updater — takes the expected digest.

**The donor lock is a deterministic projection of the release lock** (node,
Nebula and Kubo refs plus the per-node identity fields), and the release lock
carries that projection's digest. It is not a separately signed document, and it
is identical for every node except the identity fields.

### D-M7.3-17 — Tiered gates.

PR-static (hermetic) · RC/tag (Docker-capable) · release (TUN-capable).
Promotion requires the evidence tier to have passed, and the lock records which
runs produced it. A static gate may never satisfy a claim needing an executed
one. A release candidate is impossible while any gate-coverage entry is a
placeholder.

### D-M7.3-18 — Four completion states, each with a recorded write.

code complete → release candidate verified → release published → transition
evidence passed. The ROADMAP row reaches ✅ only at the fourth.

States 2–4 occur **after** the milestone merges, so each has an explicit
**post-release ledger write** that updates the ROADMAP row and the release
record. A milestone that merges at state 1 and never records the rest leaves the
roadmap permanently claiming less — or, worse, silently reading as done.

### D-M7.3-19 — No auto-update (T1.22).

A Tier-1 invariant. `UPGRADING.md` records the reason — a compromised or merely
broken release reaching every donor at once defeats the failure-domain diversity
the federation exists to have — and the conditions any future channel would need:
signed digest allowlists, staged rollout, a concurrency cap, automatic halt on
regression, operator-configurable windows, rollback only when declared safe, and
no key rotation coupled to an application update. This decision is what makes
D-M7.3-21 mandatory.

### D-M7.3-20 — Census API now, admin screen in P2-M7.6.

There is no nodes/federation admin surface to extend. M7.3 ships the
operator-only endpoint and CLI; P2-M7.6 renders it. P2-M7.4's `_admin` prefix
work requires an explicit route migration and parity test.

### D-M7.3-21 — The fleet policy: a coordinator upgrade requires no donor upgrade.

With T1.22 forbidding auto-update, each volunteer decides when their machine
changes. Long-lived backward compatibility is therefore mandatory.

#### D-M7.3-21a — The support window, executable.

A donor artifact `R` is supported by target `T` while **either** branch holds:

- **predecessor branch** — `R` is one of `T`'s two immediate donor predecessors
  (N−1 or N−2); **or**
- **age branch** — fewer than six months have elapsed since `R`'s declared
  `support_epoch`.

Support expires only when **both** are false. Note what this means: for a
*fixed* target `T`, an N−1 or N−2 artifact has **no effective expiry** —
`support_epoch + six months` is the **age-branch deadline**, not the artifact's
expiry date, and it becomes decisive only once the predecessor branch stops
holding (that is, once two further releases have shipped). Documentation states
it that way; describing the six-month date as "when support ends" would be wrong
for exactly the artifacts most likely still deployed.

The precontract **baseline has no release date**, so its `support_epoch` is
declared explicitly in the v0.3.0 intent and its age-branch deadline is a stated
date rather than an inference.

Intent, lock and catalog carry the executable metadata: supported artifact
identities (product version **or** commit identity), `support_epoch`,
`support_until`, and the **core** and **per-role** capability profiles. Without
it, census classification and `deprecation_message` have nothing to consult, and
the coordinator must consult it without network access.

#### D-M7.3-21b — Operational meaning of each condition.

Version class is policy; the interop contract is protocol + capabilities.

| Donor condition | Required behaviour |
|---|---|
| Current | Normal placement, durability, reads, repair, audits per capabilities. |
| Older but supported | **Identical operational treatment.** A warning may show; version must not reduce usefulness. |
| Missing an optional capability | Still a valid holder. Excluded only from that role. |
| Precontract / unknown version | Judged by negotiated protocol and capabilities. `unknown` is **not** incompatible. |
| Unsupported but wire-compatible | Untested, not dead. Keeps existing replicas; no automatic eviction. |
| Missing a mandatory capability | No work requiring it; existing data replaced **before** demotion or revocation. |
| No compatible protocol | A new registration may be refused; an existing donor is drained and replaced **while the old protocol still exists**. Never strand a sole replica. |
| Offline / stale | Existing liveness and healing; independent of version. |
| Digest/version mismatch | Supply-chain warning only. Never a placement or interop decision. |

#### D-M7.3-21c — Nonconformance is advisory; the operator drains.

Automatic lifecycle mutation is rejected: `draining_at` is operator-controlled
and the heartbeat path never touches it.

When an existing donor falls outside the mandatory profile: it **stays
connected and keeps its replicas**; placement queries exclude it from work
requiring the missing capability; the coordinator emits
`config_updates.deprecation_message` (row 25 — the field the protocol already
specifies) and exposes the state in the census; the **operator** invokes the
existing drain lifecycle; the existing bounded reconciliation and drain-debt
machinery performs replacement; and only a later **named release**, after the
support window, changes fresh-registration requirements.

The donor agent must consume and log `deprecation_message` — adding the response
field alone warns nobody.

Protocol retirement follows `FEDERATION_PROTOCOL.md:536-537`: introduce as
optional or dual-stack → a named deprecation release → a minimum support-until
date → no-new-placement after notice → bounded replacement → replace-then-demote
→ removal only once no supported deployment depends on it. If an incompatible
donor is the sole recoverable holder of an object, **the coordinator upgrade is
blocked** until that data lives elsewhere.

### D-M7.3-22 — `blob-transfer/v1` is route-gated.

Row 23's contradiction is resolved in favour of the P2-M7 design and
`compat_matrix_test.go`: production wiring is the outlier.

- Remove `blob-transfer/v1` from the production required profile.
- Require it at **every assignment-producing path**, not just one. Initial
  placement runs through `ListAdmissionCandidates` (`federation.sql:205`, called
  from `pkg/coordinator/admission/assigner.go:62`); healing and repair run
  through `ListPlacementCandidates`; and the DB-direct `AssignPin` seam bypasses
  both. All three are covered, with `AssignPin`'s bypass available only through
  an explicitly named test-only override. A test **enumerates the assignment
  entry points** so a fourth one cannot be added silently — otherwise
  "assignments never target a donor that cannot fetch" is simply false.
- **Preserve existing acknowledged replicas** on donors lacking it.
- Use **one exported shared profile** in `cmd/coordinator` and in tests, so the
  invariant is evaluated against production wiring.

This preserves the distinction between holding existing data and accepting new
fetch-requiring assignments, and keeps an older donor useful rather than refusing
its registration — the behaviour D-M7.3-21b requires.
