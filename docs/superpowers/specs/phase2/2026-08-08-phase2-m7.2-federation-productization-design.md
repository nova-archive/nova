## Why this milestone exists

The federation protocol works. P2-M1 through P2-M7.1 built and proved identity,
registration, assignment sync, replication, donor-backed reads, liveness,
healing, possession audits, drain, cross-version compatibility and below-floor
replacement. What does not exist is a self-consistent route from an
already-running standalone operator to "first donor registered and serving."

This is not docs drift. Several shipped deployment artifacts describe *different
systems*, and the nominal happy path — issue cert, render template, send bundle,
`docker compose up -d` — is not a valid end-to-end deployment today. The finding
was produced by trying it, not by reading code looking for trouble.

The thesis, in the findings' words: **the next marginal federation protocol
feature is less valuable than making that existing path reproducible for a second
human being.**

## Decisions

### D-M7.2-1 — Administrative tooling ships as a packaged service; issuance authority never enters a long-running container.

Add a `nova-admin` service to the federation Compose overlay, built from a new
`docker/admin.Dockerfile`: `novactl` plus a **digest-pinned** `nebula-cert`. It is
`profiles: ["federation"]` and run-to-completion (`docker compose run --rm`),
never a daemon.

Mounts are narrow and explicit:

| Mount | Purpose | Mode |
|---|---|---|
| `nova-config` | read `operator.yaml`, write the `federation:` block | rw |
| `nova-fedpki` (**new**) | Nova federation CA key, Nebula CA key, issuance state | rw |
| `nova-secrets` | install runtime identities/seeds | rw |
| `./invites` (bind) | invite bundle output | rw |
| `./import` (bind) | present a pre-existing hand-built PKI for adoption (D-M7.2-2c) | **ro** |

**The invariant:** `nova-fedpki` is mounted **only** into `nova-admin`. The
coordinator and Nebula containers get their own runtime identities and never
mount issuance authority. `federation doctor` asserts this (D-M7.2-3), because
the property is worth nothing if a later Compose edit quietly breaks it.

This is what closes finding #16 — the packaged admin service is the reason the
normal path needs no host Go toolchain and no host `nebula-cert`.

### D-M7.2-2 — `federation init` is failure-atomic with respect to activation, idempotent, and adoptive.

One command replaces the whole manual choreography:

```sh
docker compose --profile federation run --rm nova-admin \
  federation init \
  --overlay-cidr 10.42.0.0/24 \
  --operator-overlay-ip 10.42.0.1 \
  --lighthouse-public <public-ip>:4242 \
  --hostname nova.example.org
```

Ordered steps, `operator.yaml` **last**:

1. Preflight `/dev/net/tun` and host route conflicts against `--overlay-cidr`.
2. Validate the CIDR and that `--operator-overlay-ip` lies inside it.
3. Create the Nova federation CA (`ca.GenerateCA`).
4. Issue the coordinator **server** identity with correct IP and DNS SANs
   (`ca.IssueServerCert`).
5. Issue the coordinator **federation client** identity
   (`ca.IssueCoordinatorClientCert`, `nova://coordinator/<uuid>`) — required
   since P2-M4.1 for donor-backed reads, and absent from every current
   bootstrap document.
6. Generate the Ed25519 repair-token signing seed
   (`federation.repair_signing_key_path`) — never mentioned in any current
   bootstrap document, and without it the coordinator degrades to a 503 source
   endpoint.
7. Create the Nebula CA and the **lighthouse** identity + config (closes #14).
8. Install runtime secrets with explicit permissions (0600 keys, 0644 certs),
   CA keys into `nova-fedpki` only.
9. Write a **non-secret** manifest of addresses and fingerprints
   (`federation-manifest.json`) — the artifact `doctor`, `invite` and support
   read instead of re-deriving.
10. Update the `operator.yaml` `federation:` block atomically (temp → fsync →
    rename), populating `listen_addr`, `nebula_interface`, the three
    `federation_*_path` fields, `federation_client_{cert,key}_path`,
    `repair_signing_key_path` and `source_nebula_addr`.

#### D-M7.2-2a — "Atomic" means failure-atomic with respect to activation, not a cross-volume transaction.

`init` writes across at least three Docker volumes (`nova-fedpki`,
`nova-secrets`, `nova-config`). There is no transaction spanning them, and
claiming atomicity would be false. The real property, and the one the
implementation must provide:

1. **Stage.** Generate or import into a generation-scoped staging path
   (`<vol>/.staging/<gen-id>/`), never over active material.
2. **Fsync.** Every staged file and its parent directory.
3. **Validate the complete staged federation** as a unit — chains verify, SANs
   match the requested parameters, keys pair with certs, the seed parses.
   Validation happens before anything becomes visible.
4. **Activate runtime files** by rename into place. Active material is never
   overwritten in situ.
5. **`operator.yaml` last**, atomically (temp → fsync → rename). This is the
   **activation boundary**: before it, the coordinator's next boot behaves as
   though `init` never ran.
6. **Interruption leaves only staged/orphan material**, which is inert. A
   subsequent run inventories, discards unreferenced staging generations, and
   resumes.

That makes idempotence meaningful under power loss rather than only meaning
"running it twice after a success is harmless." Both are required and both are
tested: the crash-injection test interrupts after each of steps 1–5 and asserts
that a re-run converges to the same end state.

#### D-M7.2-2b — Adoption is the same code path as refuse-to-clobber, and it has an explicit preservation inventory.

Bug's deployment already has a hand-built federation CA, a hand-edited
`operator.yaml` and a donor mid-enrollment. A greenfield-only bootstrap would
make this milestone itself require the manual remediation the track forbids
(track constraint 1). So `init` always begins by **inventorying** existing state:

- Nothing present → create everything (greenfield).
- Present and consistent with the requested parameters → **adopt**: import,
  fill only what is genuinely missing (typically the coordinator client identity
  and the repair seed), write the manifest, leave existing authority untouched.
  Report exactly what was adopted vs. created.
- Present and *in*consistent (CA exists but SANs disagree with `--hostname`,
  overlay IP outside `--overlay-cidr`) → **refuse** with a diff and a named
  remedy.

**Preservation inventory — adoption must carry all of these forward unchanged:**

| # | Artifact | Consequence of regenerating it |
|---|---|---|
| 1 | Nova federation CA cert **and private key** | every issued donor cert becomes untrusted |
| 2 | Coordinator federation **server** identity | donors fail the server-cert check |
| 3 | Coordinator federation **client** identity, if present | donor-backed reads and possession audits break (P2-M4.1/M6) |
| 4 | Repair-signing seed, if present | in-flight repair grants fail `wire.Verify` |
| 5 | Nebula CA cert **and private key** | every donor loses overlay membership |
| 6 | Lighthouse identity and public address | donors cannot rendezvous |
| 7 | **Kubo `swarm.key`** | see the invariant below |
| 8 | Donor IDs, certificates, overlay-IP allocations — or enough issuance state to prevent reuse | duplicate `node_id` or overlay-IP collision |
| 9 | Coordinator DB registration state | `init` **never** touches the `nodes` table; adoption is a filesystem/PKI operation only |

**Hard invariant: the Kubo swarm key is never rotated during adoption.** A donor
already holding the key is silently partitioned from the private swarm if
bootstrap treats it as new-install material — the donor stays up, registers, and
simply cannot exchange blocks. `init` refuses to proceed if it would write a
`swarm.key` differing from one already present, and `doctor` Plane A's
`swarm.key` check compares the active key's fingerprint against the manifest.

#### D-M7.2-2c — Hand-built PKI is presented through an explicit read-only import mount.

"Inventory existing state" does not answer how `nova-admin` reaches a CA private
key living outside its four volumes — on Bug's host it is in an operator-chosen
directory that predates any of this.

`init` takes **`--adopt-from <dir>`**, backed by a read-only bind mount declared
in the federation overlay (`./import:/import:ro`, empty and harmless when
unused). The command reads the old PKI from there, validates it, and **copies**
it into `nova-fedpki` under the staging protocol above. It never requires
regeneration, never writes to `/import`, and reports each file as
`adopted-from-import` in the manifest.

`docs/UPGRADING.md` tells the existing operator exactly which files to place in
`./import` and with what names, and the `live-upgrade-e2e` (D-M7.2-11) exercises
that path with a synthesized hand-built PKI.

#### D-M7.2-2d — Destroying authority requires a named, donor-aware acknowledgement.

Generic `--force` is wrong here: overwriting generated config and destroying a
federation CA are not the same act. `--force` is **not implemented**. Instead:

- **`--replace-authority`** — destroys and recreates the federation and/or Nebula
  CA. It **refuses outright when registered donors exist** unless
  `--destroy-existing-federation` is *also* supplied, and that second flag prints
  the count of donors that will be orphaned and requires it echoed back.
- Neither flag appears in any quickstart. Both are documented in
  `docs/reference/operator-configuration.md` under a recovery heading.

Re-running `init` with identical parameters on a healthy federation is a no-op
that exits 0.

### D-M7.2-3 — `federation doctor` is split across three planes, none of which needs the Docker socket.

The original draft promised an enforcement mechanism the proposed process did not
possess. A `nova-admin` container holding only its own narrow mounts cannot inspect
another container's network namespace or mount namespace, and the fix is **not**
to hand it `/var/run/docker.sock` — that converts a deliberately narrow
administrative container into a root-equivalent Docker control plane, defeating
D-M7.2-1's entire point.

Each check is therefore assigned to the plane that can actually observe it.

**Plane A — local checks, in `nova-admin` (`federation doctor`).** Everything
visible inside its own mounts:

| id | Check |
|---|---|
| `pki.parse` | federation CA, coordinator server cert, coordinator client cert parse; each key pairs with its cert |
| `pki.sans` | server-cert SANs contain the configured overlay IP and hostname |
| `pki.seed` | the repair signing seed parses as an Ed25519 private key |
| `pki.perms` | no world-readable key material; 0600 keys, 0644 certs |
| `cfg.manifest` | `operator.yaml`'s `federation:` block matches `federation-manifest.json` |
| `swarm.key` | the active Kubo swarm key is present and its fingerprint matches the manifest (the D-M7.2-2b invariant) |

**Plane B — live overlay checks, in `nova-doctor` (`federation doctor --live`).**
A second run-to-completion service in the `federation` profile with
`network_mode: "service:coordinator"`, so it observes the coordinator's actual
network namespace. Its mounts are read-only and deliberately exclude
`nova-fedpki` — it needs the CA **cert** and the coordinator **client**
identity, never issuance authority:

| id | Check |
|---|---|
| `net.iface` | `nebula1` exists and carries the manifest's overlay address |
| `net.bind` | the federation listener is bound overlay-only on 9443 — explicitly *not* `0.0.0.0` |
| `net.mtls` | a live mTLS probe to 9443 using the coordinator client identity succeeds |
| `net.ready` | the coordinator reports `federation.ready` on its loopback diagnostic endpoint |

`net.iface` and `net.bind` are answered by the **coordinator itself** via the
loopback diagnostic endpoint introduced in D-M7.2-8, not inferred from outside.
The coordinator is the process that knows whether it bound and to what; asking it
is both simpler and more authoritative than probing around it.

**Plane C — structural custody policy (`novactl federation compose-policy`).**
The CA-key-absence property becomes a **static gate over the effective deployment
definition** rather than a runtime inspection. It consumes `docker compose config`
output (plain YAML on stdin — no privilege, no socket) and asserts:

| id | Check |
|---|---|
| `custody.fedpki` | no long-running service mounts `nova-fedpki`; only `nova-admin` does |
| `custody.import` | `/import` is mounted read-only and only into `nova-admin` |
| `custody.secrets` | no service mounts a CA private key path |

This is strictly stronger than the original runtime check: it proves the
deployment definition makes the mount **impossible**, rather than proving one
container happened not to have it at one moment. It runs as a CI gate on every PR
*and* is runnable by an operator against their own rendered config.

**Orchestration.** `make federation-doctor` runs all three planes and prints one
consolidated report; the quickstart gives that single command. Each plane is also
independently runnable, which is what support asks for. `--json` emits
`{plane, check_id, status, detail}` records.

A failing Plane A or B blocks `node invite` unless `--i-know-what-im-doing` is
passed, which records the failing check ids in `invite-manifest.json` so a broken
bundle is traceable to the decision that produced it. Plane C failing is a build
error, not an operator-overridable condition.

### D-M7.2-4 — `node invite` emits one complete runnable bundle, and proves what is *not* in it.

```sh
docker compose --profile federation run --rm nova-admin \
  node invite \
  --name alice-desktop \
  --nebula-ip 10.42.0.10/24 \
  --image ghcr.io/nova-archive/nova-node@sha256:<digest> \
  --out /invites/alice-desktop
```

Bundle contents: the canonical `compose.yaml`, a **complete** `node.yaml`, the
federation identity (CA cert, node cert, node key), the Nebula identity, the
private Kubo swarm key, Kubo hardening init, a donor `README.md`, and
`invite-manifest.json` (node id, display name, fingerprints, pinned digests,
overlay address, coordinator endpoint, doctor status at issuance time).

Two properties are load-bearing:

- **`--nebula-public-key <path>`** lets the donor generate their own Nebula
  keypair and send only the public half; the operator signs it and never holds
  the donor's overlay private key. The symmetric-secret path (operator generates
  both) stays the default because it is one fewer step for a non-technical
  volunteer, but the guide documents the stronger option.
- **A negative assertion runs before the bundle is written**, walking every file
  and failing the command if it finds the federation CA private key, the Nebula
  CA private key, any coordinator identity (server or client), the repair-signing
  seed, the master key, or the OIDC signing key. This is a test in CI *and* a
  runtime guard, because the failure mode it prevents is silent and
  unrecoverable.

`node issue`, `node issue-coordinator-client` and `node nebula-template` survive
unchanged as expert primitives. Only their documentation status changes: they
leave the quickstart and move to the reference doc.

### D-M7.2-5 — One canonical donor deployment definition; the port vocabulary is fixed.

The deployment vocabulary, applied to every artifact:

```text
4242/udp   Nebula lighthouse / rendezvous   (operator publishes; donors dial out)
9443/tcp   coordinator federation mTLS      (overlay only)
9555/tcp   donor read-source mTLS           (overlay only)
```

`8443` reverts to meaning exactly one thing: the operator's public nginx HTTPS
port. Findings #6 and #7 are closed by making the templates the single source and
regenerating `deploy/donor/*` from them.

**Single source.** The canonical templates move from `cmd/novactl/templates/` to
**`internal/deploy/templates/`** (review sub-point, accepted). `novactl` then
becomes one *consumer* of the canonical deployment definition rather than its
conceptual owner — which matters now that the same templates also generate the
checked-in `deploy/donor/*` artifacts and feed the `make gen-deploy` target.
`donor-deps-boundary` is unaffected: `novactl` is not in the donor graph, and the
package is template data plus a render function with no runtime imports.

`deploy/donor/compose.yaml` and `deploy/donor/node.yaml.example` become
*generated artifacts* checked into the tree, each carrying a prominent header
naming the authoritative source and stating that edits will be overwritten,
verified by a drift test (`make gen-deploy && git diff --exit-code`). Canonical
topology: **Nebula + hardened Kubo + `nova-node`**. Canonical paths: `/etc/nova` for public and
configuration material, `/run/secrets` for private keys — closing #10 in favour
of the `node.yaml.example` convention, because it is the one that survives a
`read_only` rootfs cleanly. Canonical storage: `storage_dir:
/var/lib/nova-node/data` with a matching named volume, closing #11.

The generated `node.yaml` carries **every field the runtime requires** —
including `kubo_api_addr`, `storage_max_bytes`, `source_nebula_addr`,
`source_read_listen_addr`, `egress_budget_bytes_per_day` and
`audit_budget_fraction` — closing #8 and #9. A drift test enumerates
`nodeconfig.Config`'s yaml tags and fails when the template omits one without an
explicit opt-out annotation, so P2-M8's new fields cannot silently reopen this.

**No mutable tags** (#12). `node invite` requires `--image` as a digest or
resolves the configured tag to one, and records it. Nebula and Kubo are
digest-pinned in the canonical topology, covered by the existing
`refresh-docker-digests.sh` and the Dependabot docker ecosystem from P2-M7.1.

The Nebula firewall stops being `any/any/any` (#15): outbound open, inbound
restricted to the read-source port from the overlay.

### D-M7.2-6 — Kubo hardening is part of the artifact, not an instruction.

`deploy/donor/compose.yaml` currently carries a comment saying Kubo "MUST be
hardened per `docs/specs/KUBO_HARDENING.md`" and then ships an unconfigured
`ipfs/kubo:latest`. A volunteer following the official path should not be able to
produce a donor that leaks into the public DHT.

The bundle ships an init script, run before the daemon, that removes public
bootstrap peers, sets `Routing.Type=none`, disables mDNS, binds API and Gateway
to loopback, disables NAT/public-exposure behaviour, and mounts the swarm key via
`IPFS_SWARM_KEY_FILE`. **A donor created by the official path is
private-by-construction**, and `doctor` Plane A's `swarm.key` check verifies the
operator side of the same contract.

**Loopback reachability is made mechanically true, not assumed.** Binding the
Kubo API to loopback only works because `nova-node` and Kubo share a network
namespace — both take `network_mode: "service:nebula"`, which is what makes
`kubo_api_addr: http://127.0.0.1:5001` resolvable across the two containers. In
ordinary separate namespaces that address is unreachable and the donor cannot pin
anything. `deploy/donor/compose.yaml` already does this; the *generated* template
did not ship Kubo at all (evidence row 8), so the property has never been enforced
on the artifact operators actually receive. The `bundle-topology` gate
(D-M7.2-10) therefore asserts that every service whose `node.yaml` references a
loopback address shares a namespace with the service providing it.

### D-M7.2-7 — Registration completes in-process; a restart is a recovery action, not a protocol step.

Finding #13, and the one behavioural bug in the milestone.

`cmd/node/main.go:96-106` reads the registration store once at boot. On a first
boot the store is empty, read-source logs `node.source.deferred` and is never
started; registration then succeeds inside `Agent.Run` with nothing watching.

Fix: the read-source server becomes startable **after** registration. On a
successful initial registration the agent updates in-memory registration state,
starts read-source **idempotently** (a second call is a no-op, so re-registration
and rotation are safe), and runs the **first heartbeat and first desired-pin
synchronization immediately**. Normal timer intervals begin after that.

This is also what makes the E2E in D-M7.2-11 assertable rather than
cadence-dependent: the test observes registration → heartbeat → sync → serving
without sleeping through a poll interval and without a restart.

### D-M7.2-8 — The overlay is additive, and the coordinator waits for `nebula1` instead of dying on it.

`deploy/operator/compose.federation.yaml`, applied as an overlay:

```yaml
nebula:
  network_mode: "service:coordinator"
  cap_add: ["NET_ADMIN"]
  devices: ["/dev/net/tun:/dev/net/tun"]
```

Sharing the coordinator's network namespace is the least disruptive shape for the
current stack: `nebula1` becomes visible to the coordinator without giving the
coordinator `NET_ADMIN` and without changing its Docker network identity (which
would break the nginx upstream and the Postgres connection). The overlay also adds
UDP/4242 publication, the runtime federation mounts, `nova-admin`, `nova-doctor`,
and the read-only `./import` bind.

**The non-federated base `docker/docker-compose.yml` is unchanged.** An operator
who never enables federation sees no diff.

#### D-M7.2-8a — The circularity, stated exactly.

`network_mode: "service:coordinator"` requires a **running** coordinator
container for Nebula to attach to. But today, with federation enabled and
`nebula1` absent, the coordinator cannot run:

- `Federation.Validate` → `checkListenOnInterface` → `net.InterfaceByName("nebula1")`
  returns an error, and that error fails **config load**
  (`internal/config/federation.go:35-39, 45-50`);
- even past that, `cmd/coordinator/main.go:512` binds eagerly and returns
  `fmt.Errorf("federation listen %s: ...")` **before** `runBoth`.

So the coordinator exits, the container restarts, and Nebula's attach target
flaps. Nebula cannot create `nebula1` until the coordinator runs; the coordinator
will not run until `nebula1` exists. This is a hard deadlock on the documented
happy path, and it is more fundamental than the hardening question the first
draft raised.

A second, quieter problem: `operator.yaml` is read **once at boot**
(`opCfg` is loaded before `runBoth`). `federation init` writing the `federation:`
block does **not** affect the already-running coordinator. Nothing in the
Phase-2 architecture makes that block hot-reloadable, and this milestone does not
add it. **A recreate is therefore a required, documented step**, not an
implementation detail.

#### D-M7.2-8b — Amend the M2 startup contract: bind-or-degrade, bounded.

P2-M2 established that the coordinator "binds the federation listener before
declaring startup success and tears down as a unit on any exit." That invariant is
correct in spirit — Nova must never declare federation ready without the overlay
listener — but its *implementation* as fail-fast-at-boot is what deadlocks. The
amendment, scoped narrowly:

1. **Interface membership leaves config validation.** `Federation.Validate` keeps
   the shape checks (`host:port` parses, the three `*_path` fields are set) and
   **no longer** calls `checkListenOnInterface`. Config validity must not depend
   on ephemeral runtime state. The check itself is retained and moves to boot.
2. **A bounded wait replaces the eager bind.** New knob
   `federation.interface_wait_seconds` (default 120; `0` restores today's
   fail-fast for anyone who wants it). The coordinator starts its public and
   admin listeners normally — the service stays alive and useful — then polls for
   `nebula1` carrying `listen_addr`'s host.
3. **On success**, it binds 9443 and marks federation ready.
4. **On timeout**, it **stays alive**, federation-not-ready, and logs a
   structured `federation.listener.wait_timeout`. It does **not** exit: exiting is
   precisely what creates the flap. Federation-not-ready is a degraded state, not
   a dead process.
5. **Teardown-as-a-unit is preserved for runtime failures.** Only the *initial*
   bind becomes retryable; a listener that binds and later fails still tears the
   process down as before.

#### D-M7.2-8c — Federation readiness gets a diagnostic surface, off the public vhost.

`/health` is pure liveness — always 200, no probes
(`internal/api/handlers/health.go:10-12`) — and it is served on the **public**
vhost, where federation topology does not belong.

Federation readiness is exposed instead on the **coordinator-only metrics
listener** already introduced by P2-M7 (D-M7-1: dedicated listener,
loopback default, operator-bound):

- a `nova_federation_listener_ready` gauge, and
- a small `/readyz` reporting `{federation: {ready, iface, bound_addr, waiting_for, since}}`.

This is what `doctor` Plane B reads for `net.iface`, `net.bind` and `net.ready`,
and what makes those checks coordinator-authoritative rather than inferred from
outside. It keeps federation topology off the public surface entirely.

#### D-M7.2-8d — The real enable sequence.

This is the sequence the quickstart, `docs/UPGRADING.md` and both E2Es use.
Step 3 is the recreate that D-M7.2-8a makes unavoidable.

1. Base operator is running normally (no federation).
2. `docker compose --profile federation run --rm nova-admin federation init …`
   — writes PKI, seeds, manifest, and the `federation:` block last.
3. `docker compose --profile prod --profile federation up -d` — **recreate** the
   coordinator so it reads the new block, and start Nebula.
4. Coordinator boots, public/admin listeners come up, federation enters
   **bounded wait** for `nebula1`.
5. Nebula joins the coordinator namespace and creates `nebula1`.
6. Coordinator observes the interface, binds 9443, flips
   `nova_federation_listener_ready` to 1.
7. `make federation-doctor` — Planes A, B, C.
8. `novactl node invite …`.

**Acceptance test, explicitly** (this is the ordering regression guard):
*coordinator starts before Nebula → remains **not-ready but alive** → Nebula
appears → federation listener binds → readiness succeeds*. Also tested: the
timeout branch leaves a live, serving coordinator with federation not ready, and
`interface_wait_seconds: 0` still fails fast.

#### D-M7.2-8e — Hardening reconciliation (unchanged, still required).

The P2-M14 hardening gives the coordinator `read_only` rootfs, `cap_drop: [ALL]`
and `no-new-privileges`. `network_mode: service:coordinator` makes the *Nebula*
container inherit the coordinator's network namespace while keeping its own
filesystem and capabilities, so the two should compose — but the interaction with
`no-new-privileges` and the tmpfs layout must be verified on a real host, not
assumed. Fallback if it does not compose: a dedicated overlay network with the
coordinator joined to it, at the cost of a second address to reason about. This is
now a subordinate risk to D-M7.2-8a, not the headline one.

**The deliberate exception.** `storage_max_bytes`,
`bandwidth_budget_bytes_per_day` and `storage_dir` stay **in** the donor
quickstart. They are consent decisions — how much disk and traffic a volunteer is
lending, and where it lives — and a volunteer must decide them before running
anything. Everything else in `node.yaml` is generated and never hand-edited.

### D-M7.2-9a — The two budget fields are distinct controls, and only one is a consent knob.

The review flagged `bandwidth_budget_bytes_per_day` (roadmap constraint, D-M7.2-9)
against `egress_budget_bytes_per_day` (evidence row 9, D-M7.2-5) as newly
introduced naming drift. It is not drift — both fields exist and mean different
things — but the spec was ambiguous about which one a volunteer sets, so the
distinction is now normative.

Per `internal/node/config/config.go`:

| Field | Origin | Required? | Semantics |
|---|---|---|---|
| `bandwidth_budget_bytes_per_day` | P2-M1 (D11) | **Yes** — `validate()` refuses `<= 0` (`config.go:110-112`) | The authoritative daily bandwidth token-bucket. The umbrella budget. |
| `egress_budget_bytes_per_day` | P2-M4.1 | No | The read-source egress budget specifically. **Inherits `bandwidth_budget_bytes_per_day` when unset and `source_nebula_addr` is set** (`config.go:81-83`). Validated `>= 0`. |
| `audit_budget_fraction` | P2-M6 | No | Fraction of the egress budget reserved for possession-audit responses; defaults to `0.01` (`config.go:84-86`). |

**The consent knob is `bandwidth_budget_bytes_per_day`** — it is the required one,
it is the one a volunteer reasons about ("how much traffic am I lending?"), and
every other budget derives from it by default. It stays in the quickstart.

`egress_budget_bytes_per_day` and `audit_budget_fraction` are **refinements**:
generated into `node.yaml` with the inherit-by-default behaviour left intact, and
documented in `docs/reference/donor-configuration.md` for a donor who wants to cap
read-serving separately from their overall budget. Neither appears in the
quickstart.

The generated template must not silently pin `egress_budget_bytes_per_day` to a
literal equal to the bandwidth budget — that would break the inheritance the
loader implements and surprise a donor who later raises only the umbrella value.
It is emitted commented-out with the inheritance explained.

Also: historical "lands in M2" comments are removed from operational files; the
Nebula PKI and Nova federation mTLS trust roots are explained as **separate**,
with an explicit statement of which secrets may leave operator custody.

### D-M7.2-10 — Drift is a CI gate, not a review responsibility.

Docs rot produced this entire finding. Six independently maintained sources had
already diverged on ports, topology, paths, secrets and milestone-era comments,
and no test noticed. New gates:

| Gate | Fails when |
|---|---|
| `docs-cli-parse` | an operator doc contains a `novactl` invocation the current binary cannot parse (closes #2–#5 permanently) |
| `gen-deploy-clean` | `deploy/donor/*` differs from what the templates generate |
| `node-yaml-complete` | a `nodeconfig.Config` yaml tag is absent from the template without an opt-out annotation |
| **`rendered-node-config-valid`** | the rendered `node.yaml` fails the **production** `nodeconfig` loader |
| `bundle-topology` | a generated bundle omits Kubo, a `node.yaml` path has no corresponding mount, or a loopback address crosses a namespace boundary |
| `invite-secret-leak` | an invite contains any operator-only secret (also a runtime guard) |
| `port-vocabulary` | 4242/9443/9555 disagree between artifacts |
| `no-mutable-tags` | an unapproved mutable tag appears in an operational template |
| **`compose-custody`** | Plane C of D-M7.2-3 — a long-running service can mount `nova-fedpki`, `/import` is writable or over-shared, or any service mounts a CA private key path |

#### D-M7.2-10a — `rendered-node-config-valid` must materialize a fixture tree.

Review point 5, with an implementation constraint the review could not have known
and that would otherwise be discovered mid-task.

Reflection over yaml tags proves **presence**; it does not prove the rendered
values parse, meet the validation floors, or agree with one another. So the gate
renders a real `node.yaml` and loads it through `nodeconfig.LoadFromBytes` — the
production path, including `validate()`.

But that loader is **not** a pure function:

- `checkReadableFile` stats and opens all six `*_path` fields and fails if the
  file is missing or is a directory (`config.go:97-109, 168-187`);
- `validate()` calls `os.MkdirAll(c.StorageDir, 0o700)` and then
  `checkWritableDir`, which **writes and removes a probe file**
  (`config.go:122-127, 148-158`).

A bare CI job pointed at the rendered template will therefore fail on missing
cert files and attempt to create `/var/lib/nova-node/data` on the runner. The gate
must consequently:

1. render into a temp root with paths rewritten to that root (the render function
   takes a path prefix, exercised only by tests);
2. materialize plausible dummy files at every `*_path`;
3. run `LoadFromBytes` and assert success;
4. additionally assert the **inheritance** contract from D-M7.2-9a — with
   `source_nebula_addr` set and `egress_budget_bytes_per_day` unset, the loaded
   config's egress budget equals the bandwidth budget.

Keep `node-yaml-complete` alongside it: it catches a newly added field the moment
it appears, whereas the loader gate only catches fields that are *required*.

These gates are cheap, hermetic, and run on **every PR**.

### D-M7.2-11 — Upgrade continuity is a release gate; `docs/UPGRADING.md` is born here.

Track constraint 1. Two E2Es, both on the privileged/self-hosted release gate
because hosted CI cannot reliably provide TUN and privileged networking:

**`federation-deploy-e2e`** (clean room). It follows **D-M7.2-8d verbatim** —
that sequence is the test, and any divergence between it, the quickstart and
`docs/UPGRADING.md` is a bug in one of the three:

1. boot the base operator Compose (no federation);
2. `federation init`;
3. `up -d` with base + federation overlay — the **recreate**, per D-M7.2-8a;
4. assert the coordinator is **alive and serving but federation-not-ready** while
   `nebula1` is absent — the ordering regression guard from D-M7.2-8d;
5. Nebula attaches, `nebula1` appears, the listener binds,
   `nova_federation_listener_ready` flips to 1;
6. all three `doctor` planes pass;
7. generate one donor invite; it passes `docker compose config`;
8. start that exact generated topology;
9. observe registration and **immediate** heartbeat/sync;
10. observe read-source start **without a restart** (D-M7.2-7);
11. prove the coordinator can authenticate to read-source;
12. drain and revoke the donor cleanly.

Two negative branches run alongside it: `interface_wait_seconds` elapsing leaves a
live coordinator with federation not ready (not a crash-loop), and
`interface_wait_seconds: 0` still fails fast for operators who want that.

**`live-upgrade-e2e`** (new, and reused by every subsequent milestone in the
track): stand up the **previous tag** with a coordinator and a **registered
donor**, upgrade to HEAD following only `docs/UPGRADING.md`, assert the
federation is healthy and the donor still sourceable, with **zero commands not in
the doc**.

For M7.2 specifically this exercises **adoption**: the fixture synthesizes a
hand-built federation in the shape Bug's deployment actually has — a CA and
coordinator identity generated outside `nova-fedpki`, a hand-edited
`operator.yaml`, an existing Kubo `swarm.key`, and a donor already registered in
the `nodes` table — presents the PKI through `--adopt-from /import`, and asserts
that after upgrade: the CA fingerprint is **unchanged**, the swarm key is
**unchanged**, the donor's `node_id` and certificate still authenticate, and the
donor is sourceable again without re-enrollment. A crash-injection variant
interrupts `init` after each staging step and asserts a re-run converges
(D-M7.2-2a).

`docs/UPGRADING.md` is created in this milestone with its own entry. It becomes
normative, generated and tooled in P2-M7.3; here it is the honest minimum: what
changed, what an existing operator runs, what an existing donor runs, and how to
go back.
