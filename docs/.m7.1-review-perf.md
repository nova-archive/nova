# P2-M7.1 Task 14 — Performance review (2026-07-06)

Scope: whether the milestone introduces a query that is slow at scale, especially
on a hot path. Reviewed inline on Opus 4.8; gate = `make bench-corpus-explain`
(index-availability, enable_seqscan=off) + reasoning against the P2-M7 9.8M-block
release-bench precedent.

## Verdict: no hot-path regression.

The only new query surface is the Task 11 below-floor sweep, which runs in the
single-leader orchestrator tick loop (60s cadence) and the scrape-time collector
(3s budget) — neither is on the request path.

- **Sweep marker maintenance** (MarkBelowFloorNodes / ClearBelowFloorNodes):
  single UPDATEs over `nodes` (a small table — donor count, not blob count).
  Trivial.
- **EnqueueBelowFloorReconcile / DemoteBelowFloorReplicas**: the only queries
  that scale with a below-floor hub donor's pin count. The demote reuses the
  EXACT hash-aggregate shape the P2-M7 corpus bench validated for
  CountDrainPendingCIDs (the correlated per-pin probe was ~23 s on a 500k-pin
  holder; the hash-aggregate is the fix). It runs at 60 s tick cadence, not the
  3 s scrape budget, so it has strictly more headroom than the already-shipped
  drain-debt scrape families. Bounded by `requeue_batch` (default 500) per tick.
- **CountBelowFloorNodes** (scrape gauge): counts only marked nodes via the 0018
  partial index — a tiny set. Cheap.

## Gate additions (commit 603d62a)

`TestExplainPlans` already asserted `nodes_below_floor_idx` for the sustained
predicate + the `pin_assignments` join indexes (Task 10). Added a case for the
actual EnqueueBelowFloorReconcile victim selection, asserting it drives from
`nodes_below_floor_idx` (few sustained nodes → nested-loop into
`pin_assignments_node_state_idx`) rather than a full `pin_assignments` scan —
the property that keeps the sweep bounded at 9.8M blocks. `make
bench-corpus-explain` green incl. migration 0018.
